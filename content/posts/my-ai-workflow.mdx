## 1. 2027 트렌드 코리아라는 책을 읽었다

연말마다 핫해지(는 것 같은)는 그 책, YYYY년 트렌드코리아 시리즈

나 또한 2027 트렌드코리아를 최근 읽었다. 

2026년을 대표하는 압도적 키워드인 AI가 2027년에도 다르지 않다는 것을 암시하듯 책 절반의 내용이 AI에 대해 다루고 있었으며 공감되는 부분이 많았다.

이 책은 AI를 연도별로 이렇게 얘기하더라

1. 2022,2023년에는 신문물 
2. 2024년에는 생산성 향상의 무기 
3. 2025년은 능숙히 다뤄야 할 도구
4. 2026년에는 **공기**처럼 변했다고 한다

도구는 필요할 때 손에 쥐는 것이지만, 공기는 존재하는지조차 잊은 채 들이마시는 것.

이제 현장에서 AI를 도입하자 라는 말은 더이상 들리지 않는다. 더이상 AI는 새로운 것을 들이는 개념이 아니고 흔히 도처에 녹아있기 때문이다.

2027년 AI에 걸맞는 단어를 예상해보자면 **뉴노멀**이 되지 않을까?

IT업종 뿐만의 얘기가 아니라 다양한 분야(ex [보험업](https://www.fnnews.com/news/202611161914312709))에서도 **AX를 조직에 안착**시키려는 여러 시도가 보이고 AI 성능이 2027년에도 J커브를 타고 초진화를 할 것 같은 느낌이 들기에.. AI를 사용함에 있어 능숙도의 차이는 있을지라도 누구나 사용하는 뉴노멀이 될 것 같다는 생각이 들었다.

<Callout type="info">
AX(AI Transformation): 단순히 업무에 AI 도구를 쓰는 것을 넘어, 조직의 일하는 방식과 프로세스, 의사결정 구조를 AI 중심으로 완전히 재설계하는 과정
</Callout>

서론이 좀 길었지만 나는 최근 2달동안 조직의 AX 도입기를 몸소 경험했고 그 과정을 평소 조직이 갖고 있던 문제 해결과 연결지어 공유해보려고 한다.

## 2. AX로 팀의 업무방식 효율화하기

### 1) 병목지점 살펴보기

피그마, 컨플루언스의 기획문서, QA팀의 체크리스트 문서 등등등 문서의 대부분은 '화면'을 기준으로 정의된다.

이 말인 즉슨 프론트엔드는 개발자는 이를 구현하는 입장에서 비교적 더 문서를 신중하게 살펴봐야한다는 말이 된다.

하지만 대부분의 경우 이 문서는 처음부터 아주 나이스하게 모든 것이 완벽한 상태로 나오진 않아 되묻는 절차가 자주 오가게 된다.

기획-디자인-개발의 프로세스 중 대부분의 시간은 기획-디자인을 정립하고 개발로 넘겨받았으나 다시 핑퐁을 해야 하는 상황에 놓이는 것이 많은 팀의 숙제라고(혹은 였었다고) 생각한다.

<Image src="/posts/my-ai-workflow/1794839438786-a6de81be-d44c-4635-ab1e-8f7a0ab57ac7.webp" width={45} alt="다만 이는 흔한 업무의 과정이다" />

사유는 팀마다 다양할 것이다.
1. 단순 디자인 누락
2. 기획한 화면 단위의 내용이 다른 페이지에서는 충돌
3. 문구 톤앤매너 및 도메인 용어 정합성 안맞음

등등등..

물론 기획과 디자인이란 무에서 유를 창조하는 구간이기 때문에 당연히 처음부터 완벽하게 나올 수 없다! 개발자와 핑퐁을 거쳐 검수하는 것은 합당한 절차이고 매우 건강한 과정이라고 생각한다. 

다만 이 구간의 소통 비용을 줄인다면 기획자와 디자이너 입장에서는 급작스런 질문이나 작업에 컨텍스트를 스위칭하는 불편을 줄일 수 있고, 더 많은 애자일 팀에 신경을 쏟을 수 있는 등 팀의 업무 효율이 더 좋아질 것 같은 건 사실이었다.

### 2) AI를 활용하여 퇴근 후의 시간 살리기

지금 회사에서는 피그마 구성이 완료되면 기획자와 디자이너가 개발자에게 기획을 설명하고 피그마 링크를 넘겨주는 '인수기준 회의'라는 것을 잡는다.

따라서 나는 기획상 허점과 디자인의 누락 등을 최대한 이 회의에서 다 짚기 위해 인수기준 회의 전날 **밤새 피그마와 기획문서간 정합성, 누락, 과적용, 문구톤 미스매치 등을 찾도록** 에이전트에게 랄프루프를 돌려 놓는다.

<Image src="/posts/my-ai-workflow/1794839894025-445c2311-4dd1-465d-ad41-6786237ce099.webp" width={100} />

그리고 다음날 오전 정리된 사항을 개인적으로 검토한 후 인수기준 회의에 참여하여 공유하는 식으로 핑퐁을 많이 줄였다.

이 작업은 기획자나 디자이너가 개발자에게 넘겨주기 전에 직접 에이전트를 돌려 검증할 수도 있지만 개발자가 해야 된다고 생각하는 이유는 **그 화면/기능 기획과 엮여 있는 다른 부분에 영향을 미치는지 코드베이스를 기반으로 짚을 수 있기** 때문이다. 

## 3. AX로 개발 프로세스 효율화하기

### 1) 기존 개발 프로세스의 문제점

인수기준 회의가 끝나면 클라이언트단은 화면작업에 바로 착수, 백엔드는 설계를 시작했다.

기존 개발 프로세스의 문제로 생각되었던 부분은.. 각 챕터별로 자율성을 주어 화면을 각자 입맛에 맞게 해석하고 작업에 착수하도록 한 것이다.

개발 라인에 들어와서도 소통 비용은 프론트엔드, 모바일, 백엔드 간에 여전히 존재하기에 소통을 줄이고 애자일하게 더 빨리 만들 수 있는 방법이라고 생각했기 때문이었다.

실제로 각 챕터별 개발 속도는 매우 빨랐다. 클라이언트를 예로 들면 피그마를 보면서 어떤 부분에서 API가 필요하겠구나 인지할 수 있으므로 그 부분을 모킹 데이터로 미리 처리해두고 작업을 하니 화면 자체를 뽑는 속도 자체는 매우 월등했었다.

하지만 막상 큰 틀로 봤을 때는 그렇게 빠른 느낌이 들진 않았다. 

1. 어떤 챕터의 작업이 빨라도 다른 챕터의 작업을 기다려야 하는 병목 현상이 있었고,
2. 완성된 API를 연동할 때 수정이 필요한 부분이 있다면 도중에 소통비용이 들게 되고, 
3. 심한 경우 API 응답 구조도 바뀌어야 하는 경우도 있었고 이 경우에는 또 병목 현상 발생

즉, 빠른 기능 출시를 위해 개발 시간을 줄이려고 각 챕터의 소통 과정을 최대한 제거한 것이었지만 시간의 총량 자체에서는 기적적인 효과는 없었다.

그리고 효율과 속도를 별론으로 하고

4. 어떤 데이터를 각 챕터만의 도메인 언어로 해석하는 문제도 있었고,
- 예를 들면 설문/토론 데이터에 대해 프론트엔드는 discussion, 백엔드는 poll, 모바일은 survey 등의 변수명을 붙여 사용하고 있었다. 
5. 또한 모바일과 같은 화면을 구성했음에도 정작 사용하는 데이터나 API가 다르다는 등 해석의 차이가 있는 경우도 있었다.
- 웹에서는 유저의 차단 상태를 A API로 표현했으나, 앱에서는 B API로 표현

챕터 간의 이해가 상충하여 발생한 문제였다.

### 2) BFF 개발 프로세스 정립

개선점은 명확했다.

1. API 연결 간 발생하는 소통 줄이기 
2. 수정이 필요하더라도 특정 챕터가 다른 챕터의 작업을 기다리지 않기
3. 도메인 용어 통일하기
4. 특정 API를 모바일과 같은 의도로 사용하기

다행히도 해결법은 복잡하지 않았고 딱 하나의 프로세스 도입으로 위 4가지를 해결할 수 있었다.

**합의된 문서를 기반으로** 클라이언트와 백엔드를 잇는 중간층 레이어 두기. 즉 **BFF를 도입**하는 것이었다.

BFF(Backend For Frontend)라고 함은 **프론트엔드(UI)의 요구사항에 맞춰 최적화된 데이터를 제공**해 주는 보조 서버이므로 진두지휘는 프론트엔드 개발자가 맡는 것이 가장 핏했다.
- 또한 사용중인 스택인 NextJS에서는 애초에 프레임워크 내 기능인 [Route Handler를 BFF용으로 사용하라고 권장](https://nextjs.org/docs/app/guides/backend-for-frontend)한다!

BFF를 도입하게 되면 그 레이어에 합의된 스펙대로 프론트엔드, 모바일, 백엔드가 각자 그 스펙을 믿고 작업을 진행하게 된다.

연결 시점에서야 하나둘 맞춰보는 것이 아닌 어떠한 **기준을 두고 작업**하는 것이기에, 설령 이 기준에 수정사항이 발생하더라도 모두가 같은 공감을 갖게 되는 것이다.

이 BFF 문서는 역시 수 번의 랄프루프를 통해서 

1. 누락된 화면 혹은 데이터 혹은 API를 찾아내는 과정을 거치고
2. 연관된 API가 이미 존재한다면 기존 API를 확장하는 방식으로 적용하는게 좋을지, 새로운 API로 분리하는게 좋을지 등

그렇게 완성된 BFF 아티팩트 문서를 백엔드와 모바일 챕터 담당자에게 전달한다

<Callout type="info">
SSOT(Single Source of Truth) : 모든 데이터나 출처를 오직 단 한 곳으로 정하고, 다른 모든 시스템이나 문서는 그 원본만을 참조하도록 만드는 정보 관리 원칙
</Callout>

그렇게 이 문서를 기반으로 개발 챕터들은 병렬로 업무를 시작한다.

- 프론트엔드: BFF API 응답에 모킹데이터 세팅 및 개발 진행
- 모바일: 개발 진행
- 백엔드: BFF API 스펙에 맞춰 백엔드 API 개발 완료 후 모킹데이터와 교체하여 실데이터 공급

이렇게 화면과 기능의 개발은 완료된다.

## 4. 팀 프로세스 AX 개선 후 성과

AX 기반의 BFF 프로세스를 도입하고 느꼈던 장점은 **정확하고, 빠르고, 모두의 생각이 같다는 점**이었다

실제 눈에 보이는 성과로도 이 프로젝트를 위해 존재한 애자일팀만 얼추 12~15팀 정도 되는 듯한데 완성되기까지 얼추 2달하고도 보름정도가 걸렸다. 

이전이라면 4~5달정도의 시간을 써야 했을 양인데 절반으로 줄어버린 것이다. 

심지어 개발 속도가 기획의 속도를 앞질러서 대기하는 시간이 있을 정도였으니... 생산성과 정확도의 발전을 경험한 프로세스 개선이었다.


## 5. 팀 프로세스 이후의 AX

이렇게 기획-디자인-개발(클라이언트-BFF-백엔드)의 싸이클을 한번 돌면 애자일 팀은 종료된다.

하지만 그 후에도 프론트엔드에게는 여전히 숙제가 남는데 바로 

1. 성능
2. UX 점검

이다. 

여기서 말하는 UX 점검은 **그 기능이 필수는 아니지만 유저가 불편을 느낄 것 같은 디테일한 부분에 한정**한다.
- 예를 들면 글 삭제 버튼을 눌렀을 때 확인 팝업 없이 곧바로 삭제처리가 되어버리는 불편한 사용감을 추적

앞선 기획-디자인 검토 단계에서 다잡지 않고 애자일 팀이 종료된 후 전수검토를 하는 이유는 크나큰 결함이나 누락이 아닌 이상 **팀의 속도에 영향을 끼치지 않게 하기 위해서**였다. 사소한 제안 하나하나가 기획자와 디자이너 입장에선 컨텍스트 스위칭 등 병목 사유가 될 수 있으니..

이렇게 정리한 사항은 개선 제안 리스트로 추려서 전달한다.

성능은 완성된 이후에만 측정할 수 있기도 하고 말이다.

성능 측정은 [performance-optimization](https://github.com/rampstackco/claude-skills/blob/main/skills/performance-optimization/SKILL.md) 이라는 스킬을 활용하고 밤새 랄프루프를 통해 개선한다.
